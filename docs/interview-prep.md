# 面接前の説明メモ

## まず自分で説明できるようにすること

1. **誰のどの作業を助けるか** — 手元に届いた新旧の告知文から、学生が日時・場所・締切・追加対応を拾い、原文で再確認する作業。
2. **入力の境界** — 文面は利用者が手で貼り付ける。大学ポータルやメールへの接続、URL巡回、保存、外部API呼び出しはしない。
3. **どのように抽出するか** — src/analyzer.js の決めたラベル、日付・時刻形式、明示的な指示表現を使い、日付を YYYY-MM-DD、時刻を HH:MM に整えて比較する。
4. **根拠と人の役割** — lineNumber と入力原文の抜粋をセットで表示する。抽出が正しそうに見えても、原文を照合する。
5. **曖昧さの扱い** — 複数の値を推測で一対一対応させない。追加と削除に分け、確認メモを出す。
6. **未解決の限界** — 年なし・和暦・PDF・言い換え・間接的な依頼・複雑な否定は扱えない。実運用データによる精度評価もまだない。
7. **テストの根拠** — 合成テキストで正常な変更、変更なし、全角数字、任意・否定表現、無効日、複数候補をテストする。
8. **AI支援の説明** — どこでAI支援を使ったかを隠さず伝え、コードとテストの意味を自分の言葉で説明できるようにする。

## 練習質問

- どうして一般のdiffではなく、日付や対応事項を分けて見せたのですか。
- どんな利用者のどんな見落としを減らしたいですか。ユーザー調査で確かめた内容と、まだ仮説の内容は何ですか。
- お知らせの解析に生成AIではなくルールベースを選んだ理由は何ですか。どの条件なら見直しますか。
- 日付の表記ゆれと、日付と申込期限が同じ文章に書かれるケースはどう扱いますか。
- 「提出は不要になりました」などの否定はどう判定しますか。誤って「提出が必要」と出たらどんな影響がありますか。
- 複数の日程が旧版・新版にある場合、なぜ自動で対応付けないのですか。
- 原文の根拠をどのように保存・表示していますか。XSSや外部送信をどう避けましたか。
- いまのテストでは何を確認し、何を確認していませんか。次に追加するテストは何ですか。
- 利用者が実際にこのツールを使う価値があるか、どのような方法で評価しますか。
- Diffcheckerやchangedetection.ioと用途が重なる部分・異なる部分は何ですか。
- AI支援を使った箇所と、自分で確認・修正した箇所を説明してください。
- 公開コードと再利用を許諾するライセンスはどう違いますか。

## 回答の組み立て方

「課題 → 具体的な利用例 → 実装判断 → 根拠/テスト → 限界 → 次の検証」の順に、実装で確認できる事実を使って答えます。市場優位性、精度、個人の開発貢献を、裏付けがないのに大きく言わないでください。

## 次の検証案

- 合成例を増やし、誤検出と見落としを分類する。
- 利用者に「元文と新文を手作業で比較した時間」「重要項目の見落とし」「確認メモが役立ったか」を聞く。
- 意味が似た複数候補、締切の取消、場所未定、オンライン化などの境界ケースをテストする。
- 実文を使う調査を行う場合は、許可と匿名化手順を先に決め、個人情報や未公開の案内をリポジトリに入れない。

## 事業仮説として話す場合

この作品は需要実証の候補ですが、顧客連絡・価格調査・課金の準備はまだ行っていません。現状は「旧新の案内を人が比べる負担があるか」「根拠付きの差分が確認に役立つか」という仮説です。事業性を説明するときも、今回の成果から言える範囲と、まだ確かめていない需要・支払い意思を分けて説明してください。
